## 二、问题一：看不到人 —— 模型上传损坏

### 现象
v1.0.19 真机画面里，玩家与敌人位置只有**灰色竖直胶囊**（`CapsuleMesh` 兜底体），没有任何人形角色。

### 诊断链路

**步骤 1：解包 v1.0.19 APK，查导入产物**

```bash
unzip -l apk19.apk | grep imported/
```

输出（关键对比）：

| 资源 | .import 字段 | 导入产物 .scn | 结论 |
|---|---|---|---|
| Knight.glb（旧 KayKit） | `path="res://.godot/imported/Knight.glb-xxx.scn"` | 1.3MB ✅ | 导入成功 |
| Rogue_Hooded.glb（旧） | 有 path | 1.3MB ✅ | 导入成功 |
| **RobotExpressive.glb（新）** | **`valid=false`** | **无 .scn** ❌ | **导入失败** |

`RobotExpressive.glb.import` 内容只有 103 字节，关键字段是 `valid=false`——Godot 导入器判定该资源无效，`load()` 返回 `null`，`_load_character()` 走兜底分支返回胶囊。

**步骤 2：从仓库下载该 glb，查文件头**

```bash
curl -L "https://gh-proxy.com/.../RobotExpressive.glb" -o repo_robot.glb
head -c 16 repo_robot.glb | od -A x -t x1z
```

输出：

```
000000 5a 32 78 55 52 67 49 41 41 41 42 30 46 41 63 41  >Z2xURgIAAAB0FAcA<
```

文件头是 ASCII 文本 `Z2xURg...`。把 `Z2xURg` 做 base64 解码 → 正好是 `glTF`。

**根因实锤**：仓库里存的 RobotExpressive.glb **不是二进制 glb，而是 base64 文本**。原文件 463,988 字节，仓库文件 618,652 字节 = 463988 × 4/3，正是 base64 编码后的长度。

### 根因

**MCP `create_or_update_file` 工具的 content 参数被当作明文存储，而非 base64 解码后的二进制**。

调用链：
1. 我本地读 glb（二进制 463988 字节）
2. base64 编码成字符串（618652 字符）
3. 传入 `create_or_update_file` 的 `content` 字段
4. MCP 服务器内部**又做了一次 base64 编码**发给 GitHub Contents API
5. GitHub 解一层 base64 → 得到我传的 base64 文本字符串 → 当作文件内容存储
6. 仓库里的文件 = base64 文本（损坏）

Godot 导入器读文件头发现不是 `glTF` magic → `valid=false` → 角色变兜底胶囊。

> **同样的损坏也发生在**：`Asian_F_1_Casual.glb`、4 个 RPM 动画 glb（`F_Standing_Idle_001.glb` 等）。所有用 `create_or_update_file` 上传的二进制 glb 全部损坏。

### 修复方案

**改用 .gltf 纯文本格式**（JSON + data URI 内嵌 buffer），走文本通道推送。

转换器（Python，无依赖）：

```python
def glb2gltf(glb_path, gltf_path):
    # 解 glb 的 JSON chunk + BIN chunk
    # 把 BIN chunk base64 编码成 data:application/octet-stream;base64,XXX
    # 写进 gltf JSON 的 buffers[0].uri
    # 贴图同理内嵌
```

验证：
- `RobotExpressive.gltf` 578KB（纯 JSON 文本）
- `buffers[0].byteLength` = 381256 = 原 BIN chunk 长度 ✅
- 14 个动画名完整保留 ✅

推送方式：`push_files`（文本通道，content 是明文字符串，不会被双重编码）。World.gd 模型路径从 `.glb` 改成 `.gltf`。

### 验证修复
v1.0.20 构建后，APK 的 `RobotExpressive.gltf.import` 应有正常 `path=...scn` 字段，角色不再是胶囊。

## 三、问题二：动不了 —— 横屏声明被 ROM 忽略

### 现象
画面横向铺在竖屏中间，上下大黑边（letterbox）。摇杆画在画面里，但触摸坐标在竖屏坐标系，与 UI 渲染坐标错位 → 点不动。

### 诊断链路

**步骤 1：查仓库配置**

```bash
curl ... project.godot | grep orientation
# window/handheld/orientation=0  ✅
curl ... export_presets.cfg | grep orientation
# screen/orientation=0  ✅
```

仓库配置正确，landscape 已声明。

**步骤 2：解包 v1.0.19 APK，解析 AndroidManifest**

```python
from pyaxmlparser import APK
apk = APK('apk19.apk')
xml = apk.get_android_manifest_xml()
# activity=com.godot.game.GodotApp  screenOrientation=0
```

**manifest 里 screenOrientation=0（landscape）已经正确写入**。

**步骤 3：对比 v1.0.18 / v1.0.19**

| 版本 | 构建时间 | manifest screenOrientation | 用户实测 |
|---|---|---|---|
| v1.0.18 | 11:20 | 0 (landscape) | 竖屏 letterbox |
| v1.0.19 | 11:33 | 0 (landscape) | 竖屏 letterbox |

两版 manifest 都是横屏，但用户手机都没旋转。且 v1.0.19 画面比 v1.0.18 亮（曝光修复生效）——**证明用户装的就是新版**，不是装错版本。

### 根因

**用户的手机 ROM（vivo 系 OriginOS 疑似）忽略了 AndroidManifest 的 screenOrientation 声明**。

理论上 `screenOrientation="landscape"` 是 Activity 级强制方向，系统应遵守。但部分国产 ROM 对 Godot 这种"非原生 Activity + 运行时渲染"的应用，方向处理存在兼容性问题，导致声明被无视。

### 修复方案

**引擎运行时再强制一次横屏**（manifest + 运行时双保险）：

```gdscript
# World.gd _ready() 开头
DisplayServer.screen_set_orientation(DisplayServer.SCREEN_LANDSCAPE)
```

Godot 的 DisplayServer 在运行时调用 Android 的 `setRequestedOrientation`，与 manifest 声明形成双通道锁定。

### 验证修复
v1.0.20 启动时引擎主动设横屏。若该 ROM 仍无视，终极方案见文末"待办"。

## 四、问题三：石头圆球竖立

### 现象
石头是竖起的圆球，半个球露地面，不像石头。

### 根因
`_build_rocks()` 用 `SphereMesh`（radius=1, height=1.2），`origin.y` 仅 `0.15~0.42 × scale`，球心贴近地面，半个球露出 → 视觉上像立着的圆球。

### 修复
换 `CylinderMesh` 压扁（top_radius=1.15, bottom_radius=1.35, height=0.62），`radial_segments=5` 出五边形硬棱角，`scale.y` 压到 0.4~0.7 → 扁平多边形块石，符合水墨皴擦质感。

## 五、环境调亮（顺带修复）

v1.0.18 画面过暗，根因是**侧视相机与太阳方向形成逆光**：

- 相机在 +Z 看向 -Z
- 太阳 `rotation_degrees=(-38, 132, 0)` → 光指向 +Z 方向 = **照相机背**，角色正面背光成黑影

修复（Environment.gd）：

| 参数 | 旧值 | 新值 | 说明 |
|---|---|---|---|
| tonemap_exposure | 0.82 | 1.18 | 整体提亮 |
| sun_energy | 2.75 | 3.8 | 主光增强 |
| ambient_energy | 0.30 | 0.62 | 环境光补暗部 |
| sun.rotation_degrees | (-38, 132, 0) | (-50, 20, 0) | 改顺光：太阳从 +Z 侧照向角色正面 |

## 七、经验沉淀（坑表）

### 坑 1：MCP 二进制上传双重编码
- `create_or_update_file` 的 content 是 string，传 base64 会被当明文再编码一次
- **所有二进制资源（glb/png/bin）走该通道都会损坏**
- 规避：二进制转文本格式（gltf data URI、base64 内嵌），走 `push_files` 文本通道

### 坑 2：Godot 导入失败静默兜底
- glb 导入失败时 `.import` 写 `valid=false`，不报错，运行时 `load()` 返回 null
- `_load_character` 有兜底胶囊，游戏不崩但角色消失
- 规避：解包 APK 查 `.godot/imported/` 是否有 .scn 产物，无即导入失败

### 坑 3：manifest orientation 不被 ROM 遵守
- 国产 ROM（vivo/OPPO 系）对非原生 Activity 的方向声明处理异常
- 规避：引擎运行时 `DisplayServer.screen_set_orientation` 双保险

### 坑 4：侧视相机与太阳方向
- 横版侧视相机在 +Z，太阳若在 -Z 侧就是逆光
- 规避：太阳方向要随相机方向调整，保证角色正面受光

### 坑 5：versionCode 不递增导致覆盖安装失败
- `export_presets.cfg` 的 `version/code=1` 恒定，同 versionCode 覆盖安装可能被 ROM 拦截
- 规避：CI 里 versionCode 按 run_number 递增（待实施）
